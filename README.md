# B_BoardGames

対面で集まって遊ぶボードゲームを、各自スマホのブラウザで補助するためのシンプルなSPAです。

対応ゲーム（2026-07時点）

- ワードウルフ（Wordwolf）
- コードネーム（Codenames）
- ラブレター（LoveLetter）
- 犯人は踊る（Hannin）
- おえかきバトル（Oekaki）… AI判定にGemini APIを使用（後述）
- おえかきバトル リレーモード（Oekaki Relay）… 2人用・非同期。ロビーを使わず、URLをLINE等で渡し合って遊ぶ

このアプリは「静的ファイル + Firebase Realtime Database」で動きます。

---

## 1) 全体像（引継ぎ用まとめ）

### 目的

- 全員が同じURL（GitHub Pages等）にアクセス
- GMが「ロビーを作成」し、参加者はQRから参加
- **QRなしでも参加可能**: 同じURL（PWA含む）を開くと、ホーム画面に「いま ひらいているロビー」が表示され、タップでQR参加と同じ導線に入る（後述の `lobbies/_index`）
- ロビーでゲーム種別を選び、各ゲーム画面へ遷移
- 進行中に“全員をロビーへ戻す”導線を提供
- PWAとしてホーム画面に追加でき、新バージョンは自動アップデートされる

### 重要な設計方針

- 1ファイルSPA（主に `bbg.js`）で画面ルーティング/描画/DB購読を完結
- Firebase Realtime Database を“状態の唯一の正”として扱う
- 画面は URL クエリで切り替える（`?screen=...&lobby=...&room=...`）
- 個別の「ロビーへ」ボタンは原則廃止し、ヘッダータイトルをクリックしてロビー復帰（= 全員強制復帰）

---

## 2) 画面/URL仕様（ルーティング）

基本：`index.html` を開き、クエリで画面を決めます。

よく使うパラメータ

- `screen`: 画面ID（例: `lobby_host`, `lobby_player`, `codenames_host`, `codenames_table` など）
- `lobby`: ロビーID（4桁）
- `room`: ゲームルームID（ランダム）
- `host=1`: ホスト/GM系画面
- `player=1` または `player=<memberId>`: プレイヤー画面
- `gmdev=1`: 「テーブル表示専用端末」（参加者としては参加しない端末）
- `v`: キャッシュバスター（`release.ps1` が `index.html` に付与）

ホーム画面のボタン

- 「ロビー作成（この端末もゲームに参加）」: 作成者が参加者としても参加する
- 「ロビー作成（この端末をゲームマスターデバイス）」: 作成者は“テーブル端末”扱い（参加者としては入らない）
- 「おえかきバトル（リレー）」: ロビーを作らずに始める2人用の非同期モード（`?screen=oekaki_relay_create`）

---

## 3) 役割（端末の種類）

端末は大きく3種類の振る舞いをします。

1. 参加者端末
   - QR参加
   - 進行に応じて各ゲームの“参加者画面”へ
2. GM参加者端末
   - 参加者として入るが、GM操作（開始/設定など）も持つ
   - コードネームのタイマー設定画面などに入る
3. テーブル端末（`gmdev=1`）
   - テーブル表示（盤面/全体情報）を主用途
   - “参加者として入らない”ことが重要（参加者と同じ扱いにするとUI/遷移が崩れるため）

## 4) Firebase（保存場所/データモデルの考え方）

Realtime Database を使い、複数端末で同じ状態を共有します。

### 4.1 ロビー

パス：`lobbies/<lobbyId>`

概念

- 参加者一覧（`members`）と表示順（`order`）を保持
- 現在プレイ中のゲーム（`currentGame`）を保持
  - ここが「全員強制的にロビーへ戻す」スイッチ

代表的なフィールド（概念）

- `hostMid`: ロビー作成者（memberId）
- `members/<memberId>`: `{ name, joinedAt, lastSeenAt, isGmDevice? }`
- `order`: memberId配列（表示順/ゲームの席順の基礎）
- `currentGame`: `null` or `{ kind, roomId, startedAt }`
- `lastKind`: 直前に遊んだゲーム種別
- `loveletterExtraCards`: ラブレター追加カード
- `codenamesAssign`: コードネームのチーム/役職割当

#### 4.1.1 ロビー一覧インデックス（`lobbies/_index/<lobbyId>`）

ホーム画面の「いま ひらいているロビー」一覧のための軽量インデックス。

- 内容: `{ createdAt, updatedAt, kind, names, count, hostMid, mids }`
- 更新タイミング: ロビー作成 / メンバー参加・名前変更 / ゲーム開始・終了（`updateLobbyIndex`）
- **なぜ本体（`lobbies` 全読み）を使わないか**: 本番のDBルールはパス列挙型で `lobbies` 直下の一括読み取りが拒否されるため。`_index` は `lobbies/$id` のワイルドカードにマッチして読めるパターンを使う（`_config` と同じ理屈）
- `_` 始まりなので `cleanupOldRooms()` の削除対象外。古いエントリ（7日超）はホーム表示時に「ついで掃除」で削除する（`pruneLobbyIndex`）
- ホームの一覧は直近12時間のロビーだけ表示。端末が該当ロビーのメンバーなら「もどる」、作成者なら「ホストでひらく」、それ以外は「さんかする」（=QR参加と同じ `lobby_join` へ）

### 4.2 ゲームルーム

ゲームごとに別のパスを使います（同一構造ではありません）。

- ワードウルフ: `rooms/<roomId>`
- コードネーム: `codenamesRooms/<roomId>`
- ラブレター: `loveletterRooms/<roomId>`
- 犯人は踊る: `hanninRooms/<roomId>`
- おえかきバトル: `oekakiRooms/<roomId>`
- おえかきバトル（リレー）: `oekakiRelayRooms/<roomId>`

いずれも「ホストが作成 → 参加者がjoin → 以降はroomの状態遷移で全画面が追従」という流れです。
（リレーモードだけはロビーを経由せず、URLを人づてに渡して非同期に進めます。§6.6参照）

---

## 5) “ロビーへ戻す”仕様（最重要・横断仕様）

基本方針

- 進行中ゲームを終了/中断して全員をロビーへ戻す操作は、ロビーの `currentGame` を `null` にすることで実現します。
- これにより、参加者端末がロビー監視で「ゲームが無い」ことを検知し、ロビー画面へ戻れます。

UI

- 各ゲーム画面の個別「ロビーへ」ボタンは削除し、ヘッダーのタイトルクリックで統一（実装上は上記の `currentGame=null` をトリガー）

---

## 6) ゲーム別仕様メモ（保守/AI引継ぎ用）

### 6.1 ワードウルフ

- 参加者は個別にワード/役職を見て進行
- タイマー表示あり
- 多数派側の参加者画面では“残り 00:59”の常時表示を抑制（UI簡素化）

### 6.2 コードネーム

- ロビーでチーム（赤/青）と役職（スパイマスター/工作員）を決定
- `lobbies/<id>/codenamesAssign` に割当が保持される
- タイマー設定画面（GM参加者端末）で「スタート」を押すとゲーム開始

重要: 役職保持の実装ポイント

- ルーム開始時に、ロビーで決めた役職がルーム側に反映されていないと開始条件チェックに失敗します。
- そのため開始時に「ロビーの割当をルームの players に適用」する処理が入っています。
- 正規化ルールとして「各チームの spymaster は必ず1人」に揃えます。

### 6.3 ラブレター

- テーブル画面から個別「ロビーへ」ボタンは削除（ヘッダークリックに統一）

### 6.4 犯人は踊る

- テーブル表示とプレイヤー表示があり、テーブル端末（`gmdev=1`）の扱いに注意

### 6.5 おえかきバトル

- 全員が同じお題を制限時間内に描き、AI（Gemini）が100点満点で採点＋一言コメント→ランキング発表
- **1人でも開始可能**（最小人数=1）。1人のときは順位表示なし・「さいてんけっか」としてスコアのみ表示
- ゲーム内のテキストは**すべてひらがな/カタカナ**（AIのコメントもかな指定）。お題リストもかな表記
- 描画画面は**フルスクリーン**（`position:fixed`）。キャンバスの内部解像度は表示領域のアスペクト比に合わせ長辺640に正規化（スマホ縦長/タブレットどちらも画面いっぱい）
- **画面回転**は `ResizeObserver`＋段階的な測り直しで追従し、サイズが2回続けて同じ値になってから作り直す（回転途中の値で作ると歪む）。描かれている範囲だけを取り出して置き直すので、回転を繰り返しても絵が縮んでいかない
- お題は **ようじ135 / しょうがくせい143 / おとな125＝計403個**（すべてかな表記。直前と同じお題は再抽選）
- 道具はキャンバスに重ねず、お題と同じ帯にまとめる（**左=お題 / 中央=🎨・もどす↩︎・やりなおす↪︎ / 右=かんせい！・タイマーリング**）。スマホ縦幅では道具のみ2段目
- 🎨で開くパネルに描画ツールを集約（13色〈うすだいだい入り・白はけしゴムで代用〉+けしゴム+スタンプ+ふとさ+ぜんぶけす）
- もどす／やりなおすは1操作ごとのキャンバス控え方式で最大10手（ぜんぶけすも取り消せる。回転で解像度が変わったら控えは破棄）
- ふとさは実寸プレビュー（スライダー横の丸）＋描画中のペンサイズ枠（ポインタに追従するリング）で分かるようにしている
- スタンプは48種のプールからラウンドごとに8個ランダム抽選（同一ラウンド内は並び固定）
- タイマーは右上の**円形リング**（SVG stroke-dashoffset）。**残り10秒でキャンバス枠が赤点滅**（`.ok-warn`）
- 演出: 提出スタンプ/judging中の鉛筆アニメ/結果カードの段階表示/スコアのカウントアップ（`setTimeout`ベース。rAFはバックグラウンドで止まるため不使用）
- **開始時カウントダウン**: `endsAt - drawSeconds*1000` をラウンド開始時刻とし、それより前は 3→2→1→「かいて！」を最前面オーバーレイ表示（サーバー時刻基準で全端末同期。`OEKAKI_LEAD_MS=3500`）
- **判定サスペンス**: 判定中は提出された全員の絵をギャラリー表示（ゆっくり脈動）。結果書き込みは `judgingAt` から最低12秒（`OEKAKI_JUDGE_MIN_MS`）待ってから行う（絵ゼロ/キー未設定時は即時）
- 画面は `oekaki_player` の1つ（phaseで 描画/待機/判定中/結果 を切替。gmdev端末は進行状況表示のみ）
- ロビー設定: 制限時間（30秒〜3分、30秒刻み）/ お題（ランダム＋対象年齢3段階 or 自由記入）
- 絵は 480×480 JPEG(base64) で `oekakiRooms/<id>/players/<pid>/image` に保存（Storage不使用）
- 判定はホスト端末（URLに `host=1`）だけが実行。phaseのCASトランザクションで二重判定を防止
- タイマーは既存同様 `round.endsAt`（サーバー時刻基準）。時間切れは各端末が自動提出（何も描いていない場合は未提出扱い）
- 「もういっかい」（ホストのみ）で同室のまま新お題の次ラウンドへ（累積ポイントなし）
- API失敗/キー未設定時は「AIなし発表」にフォールバック。結果画面から再判定も可能
- **途中参加OK**: ゲーム進行中にロビーへ入った人は `oekaki_player` に遷移した時点で自動的にルームへ登録される（`routeOekakiPlayer` の auto-join。名前はロビーのメンバー名を使用）。描画中なら残り時間で描け、判定中/結果表示中なら「もういっかい」の次ラウンドから参加

### 6.6 おえかきバトル（リレーモード）

同じ場所に集まらない2人が、**URLを手渡し（LINE等）しながら交互に描く**投稿型モード。ロビー・QRは一切使わない。

#### 進行

```
ホーム「おえかきバトル（リレー）」→ oekaki_relay_create（ホストが名前と設定を決める）
  → 部屋作成（oekakiRelayRooms/<roomId>）→ oekaki_relay
  → ホスト(a) が先に描いて提出 → 共有ボタンでURLを相手に渡す
  → 挑戦者(b) がURLを開いて名前登録 → 同じお題を描いて提出
  → b の端末でAI採点 → b が結果を見る
  → b が「結果を送る」でホストにURLを返す
     （合わせて「再戦を申し込む」を選ぶと、b が次戦の設定を決めて同じURLで送る）
  → a がURLを開くと 前回結果 ＋「第N戦 あなたの番」が出て、そのまま次戦を開始
```

- **URLは最初から最後まで同じ**（`?screen=oekaki_relay&room=<id>`）。共有は毎回「同じリンクを送り返す」だけでよい
- 先に描くのは**常にホスト(a)**。設定を決めるのは**再戦を申し込んだ側**（`settings.setBy` / `rematchBy`）。これで「お題を決めた人だけが有利」にならないよう交互になる
- 共有は Web Share API（LINE等の共有シート）→ 非対応環境ではクリップボードへコピーにフォールバック

#### 席（スロット）と本人確認

- プレイヤーは `a`（ホスト＝先攻）/ `b`（挑戦者＝後攻）の**2スロット固定**。どちらの席かは端末の localStorage（`bbg_okrelay_slot_v1_<roomId>`）に持つ
- `b` の確保は claim トークン付きトランザクション。同時に開かれても1人しか取れず、あぶれた端末は**観戦モード**になる
- LINE内ブラウザ↔Safari のように**別ストレージで開き直すと席の記録が消える**。参加画面・観戦画面から「〇〇として続ける」で席を選び直せる救済導線を用意している

#### 非同期ならではの相違点（同室モードとの差）

| | 同室モード | リレーモード |
|---|---|---|
| タイマー | 全員共通の `round.endsAt` | **プレイヤーごと**の `players/<slot>/endsAt`（「はじめる」を押した時点から） |
| お題の開示 | 開始と同時に全員へ | **自分が「はじめる」を押すまで隠す**（先に見て考える時間差をなくす） |
| 時間切れ | 何も描いていなければ未提出扱い | 相手を待たせるので**白紙でも自動提出**して進める |
| 判定実行 | ホスト端末のみ | **後攻(b)の端末**（＝両者提出がそろった時点で居る端末）。CASで二重実行を防止 |
| 画面を離れたまま時間切れ | 未提出 | 戻ると「もう一度はじめる」で同じラウンドを再開できる（`okrRestartTurn`） |

- 再戦時は `players` の画像を消すため、前回の結果カードが「画像なし」にならないよう **`prevResult.entries[].image` に絵を退避**してから次戦を用意する（`okrRematch`）
- 保持されるのは直前の1戦ぶんのみ（`prevResult`）。通算スコアは持たない

#### AIコメント（煽り採点）

- **勝った側は最大級に絶賛／負けた側は容赦なくけなす**プロンプト（`okrJudgePrompt`）。同室モードの「かな＆ポジティブ」プロンプトとは別物
- スキーマも別（`OKR_JUDGE_SCHEMA`）で、2人ぶんの `entries` に加えて勝敗を告げる煽り実況 `verdict` を返させる
- **プロンプトでガードレールを明示**: けなす対象は「その絵の出来ばえ」だけに限定し、容姿・人格・知性・性別・年齢・出身・職業への攻撃や差別的表現、暴力的・性的表現を禁止している。倫理面だけでなく、**Geminiの安全フィルタで採点ごと落ちるのを防ぐ**意味もあるので、プロンプトを緩める場合はこの点に注意
- 画面にも「けなされて笑える仲の相手とだけ遊んでください」の注意書きを出している

#### 実装メモ

- 描画UI（キャンバス／ツールパネル／もどす・やりなおす／回転追従／全画面）は **`createOekakiDrawEngine(ui, opts)` に共通化**され、同室モードとリレーモードで共有している。DOMは `oekakiDrawFsHtml()` が組み立てる（`#okCanvas` ほかのidが前提）
- 画面テキストは、同室モード＝ひらがな中心（子供向け）／リレーモード＝**通常の日本語**（大人向け）と使い分けている。描画画面だけは共通なのでひらがな表記のまま
- Gemini呼び出しは `oekakiCallGemini(apiKey, prompt, schema, entries)` にプロンプトとスキーマを渡す形

## 7) Firebase セットアップ

### 7.1 推奨: ブラウザで設定（配布が簡単）

1. Firebase Console でプロジェクト作成
2. Realtime Database を作成（開発中はテストモードでも可）
3. Web アプリを追加して「Firebase SDK の設定（構成）」をコピー
4. アプリの `?screen=setup` 画面に JSON を貼り付けて保存

### 7.2 設定をコードに埋め込む（配布先URLに固定したい場合）

- `bbg-config.js` の `ENABLE_EMBEDDED_FIREBASE_CONFIG = true` にする
- Firebase Console の `firebaseConfig` を貼り付け

### 7.3 Realtime Database ルール（開発用の最低限）

用途に合わせて必ず強化してください。

```json
{
  "rules": {
    "lobbies": { ".read": true, ".write": true },
    "rooms": { ".read": true, ".write": true },
    "codenamesRooms": { ".read": true, ".write": true },
    "loveletterRooms": { ".read": true, ".write": true },
    "hanninRooms": { ".read": true, ".write": true },
    "oekakiRooms": { ".read": true, ".write": true },
    "oekakiRelayRooms": { ".read": true, ".write": true }
  }
}
```

※ おえかきバトルを追加した場合、既存プロジェクトでも `oekakiRooms` のルール追記が必要です（無いと「ゲーム開始」が PERMISSION_DENIED になります）。

#### ⚠ リレーモードを使う前に（既存プロジェクトでの1回だけの作業）

おえかきバトル リレーモードは新しいパス `oekakiRelayRooms` を使います。**このルールを足していないと「この設定ではじめる」で PERMISSION_DENIED になり、部屋が作れません**（既存ゲームには影響しません）。

DBルールはアプリのソースではなく Firebase Console 側の設定なので、リリース（GitHub Pagesへの反映）とは別に手作業での追記が必要です。

1. Firebase Console → 対象プロジェクト → **Realtime Database → ルール**
2. **`"rules"` の中（`oekakiRooms` などと同じ階層）に** `oekakiRelayRooms` を追記する。既存のルールは消さない
   - ⚠ よくある失敗: 一番外側の `}` の**後ろ**に足してしまうと「JSONとして壊れている」として公開できません。必ず `"rules": { ... }` の**内側**に入れること
   - ⚠ 書き方は**既存のルールと同じ形式に合わせる**こと（下記2パターン）
3. **公開（Publish）** を押す。反映は即時で、アプリ側の再デプロイは不要

**パターンA: 既存が `$roomId` ワイルドカード形式の場合**（本番はこちら）

```json
"oekakiRooms": {
  ".indexOn": ["createdAt"],
  "$roomId": { ".read": true, ".write": true }
},
"oekakiRelayRooms": {
  ".indexOn": ["createdAt"],
  "$roomId": { ".read": true, ".write": true }
},
```

**パターンB: 既存がトップレベル許可のフラット形式の場合**

```json
"oekakiRooms": { ".read": true, ".write": true },
"oekakiRelayRooms": { ".read": true, ".write": true }
```

いずれの場合も、直前の行の末尾に**カンマ**が要る点に注意してください。リレーモードがアクセスするのは `oekakiRelayRooms/<部屋ID>` とその配下だけなので、パターンAのワイルドカードで過不足なく動きます。

確認方法: ホーム画面 →「おえかきバトル（リレー）」→ 名前を入れて「この設定ではじめる」で、エラーにならず描画画面の手前（「はじめる」ボタン）まで進めばOKです。

※ 現在の本番ルールは「`lobbies/$id` 単位の許可」になっており、`lobbies` や `rooms` などの**トップレベル一括読み取りは拒否**されます。このため `cleanupOldRooms()`（7日超の部屋の自動削除）は毎回 permission_denied で空振りしています。自動削除を効かせたい場合は、上記のようにトップレベルに `.read` を付ける（＋`.indexOn: ["createdAt"]` 推奨）ようConsoleでルールを変更してください。ホームのロビー一覧は `lobbies/_index` を使うため、**ルール変更なしでも動作します**。

### 7.4 Gemini APIキー（おえかきバトルのAI判定）

おえかきバトルは、全員の絵を Gemini API（無料枠あり）で採点します。

1. [Google AI Studio](https://aistudio.google.com/app/apikey) でAPIキーを無料発行（Googleアカウントのみ）
2. **ゲームを開始するホスト端末**で `?screen=setup` を開き、「Gemini APIキー」欄に貼り付けて保存
   - 参加者の端末には不要です。キーはその端末の localStorage に保存され、以降ずっと保持されます

※ **リレーモードだけは採点を後攻（挑戦者）の端末が実行します**。挑戦者はキーを入力していないのが普通なので、下記のDBバックアップ（`lobbies/_config/geminiKey`）から自動で読み込みます。どこか1台でキーを保存してあれば、URLを受け取った相手の端末でもそのまま採点できます。キー未設定のまま遊ぶと、絵は並びますが点数と煽りコメントは出ません。

#### キーの自動バックアップ（PWA/ホーム画面追加対策）

iPad/iPhoneの「ホーム画面に追加」はSafariと**別のlocalStorage**になるため、そのままではキーが引き継がれません。対策として、保存されたキーは自動で Realtime Database の `lobbies/_config/geminiKey` にもバックアップされ、**キーを持たない端末（PWA含む）は起動時にDBから自動復元**します。つまり、どれか1台で一度キーを保存すれば、以降は全端末・PWAで入力不要です。

- 注意: DB上のキーは「DBのURLを知っている人なら読める」状態になります（このアプリのDBルールは公開読み書きのため）。課金アカウントを紐付けていない限り、漏れても無料枠が消費されるだけで料金は発生しません
- `lobbies/_config` は設定用ノードです。`cleanupOldRooms()` は `_` 始まりのキーを削除対象から除外しています

#### キーを別の端末に渡す（QR / リンク / コピー）

一度キーを入れた端末の `?screen=setup` 画面には、キーを他の端末へ渡すための **QRコード・共有リンク・コピーボタン**が表示されます。

- 別の端末でQRを読み取る（または共有リンクを開く）と、その端末に自動でキーが取り込まれます（`#gkey=` フラグメント経由。読み込み後はURLから即座に除去されます）
- ⚠ 共有リンク/QRには**キーそのものが含まれます**。SNS等に公開せず、仲間内での受け渡しだけに使ってください

#### なぜ `bbg-config.js` に埋め込まないのか

このリポジトリは公開（public）で GitHub Pages 配信のため、`bbg-config.js` にキーを埋め込むと**配信ファイルから誰でも読めてしまいます**。加えて GitHub のプッシュ保護がシークレットを検知して push をブロックします。また Gemini の新形式キー（`AQ.` 始まり）は Google 側の仕様で HTTPリファラー制限をかけられず（サービスアカウントにバインドされIP制限のみ）、安全な埋め込みができません。そのため**「ホスト端末に1回入力＋QR/リンクで端末間コピー」**方式を採用しています。

キー未設定でもゲームは動作します（AI採点なしで絵の発表のみ）。判定は1ラウンドにつきAPI1リクエスト（全員分の絵をまとめて送信）なので、無料枠で十分足ります。課金アカウントを紐付けていなければ、万一キーが漏れても消費されるのは無料枠のみで料金は発生しません。

## 8) 開発/公開

### 8.1 ローカル起動

`file://` 直開きは Firebase 読み込みが失敗することがあるため、ローカルサーバーで開いてください。

PowerShell例（Pythonがある場合）

```powershell
cd "c:\Users\B\Desktop\自作ソフト\B_BoardGames"
python -m http.server 8000
```

### 8.2 GitHub Pages 公開

1. GitHub に push
2. Settings → Pages → Branch を設定
3. 公開URL（例: `https://<user>.github.io/<repo>/`）で利用

### 8.3 PWA（ホーム画面追加）と自動アップデート

各自のスマホ/タブレットで公開URLを開き「ホーム画面に追加」すると、アプリのように起動できます。

仕組み（`sw.js` + `index.html` の登録スクリプト）:

- キャッシュは `bbg-cache-<SW_VERSION>` で世代管理。`SW_VERSION` は `release.ps1` がリリースごとに自動更新する
- 同一オリジンのアセットは**キャッシュ優先＋裏で更新**（PWAを開いた瞬間に表示される）。`?v=` は無視して照合
- リリースすると `sw.js` の内容が変わる → ブラウザが新SWをインストール（最新アセットを再取得）→ `controllerchange` でページが**自動リロード**され最新版に切り替わる（「✨ こうしんしました」トースト表示）
- 更新チェックは起動時・フォアグラウンド復帰時・30分ごと
- ゲームルーム表示中（URLに `room=` あり）は自動リロードしない（描きかけの絵などを守る）。次にロビー/ホームへ戻ったタイミング以降で反映
- `localhost`/`127.0.0.1` はネットワーク優先（開発中の編集がすぐ反映される）
- QRライブラリ/Firebase SDK のCDNもキャッシュし、起動を高速化

### 8.4 `release.ps1`（stable/devの分離）

`index.html` の `?v=`（キャッシュバスター）と `sw.js` の `SW_VERSION` を更新→commit→push を自動化します。

- stable（通常の公開URL / origin）
  - `./release.ps1 -Channel stable -Message "release"`
- dev（開発用の別URL / dev）
  - `./release.ps1 -Channel dev -Message "dev"`
- 両方
  - `./release.ps1 -Channel both -Message "release"`

## 9) 保守メモ（AIに渡す時に伝えること）

- まず `lobbies/<id>/currentGame` が“全体の遷移スイッチ”であることを理解する
- URLクエリの `gmdev=1` はテーブル端末を意味し、参加者として join しない前提のUI/遷移がある
- コードネームは「ロビー割当 → ルーム反映」が開始条件に直結する
- 端末制限（参加者端末がホームに戻れない等）は、誤操作防止のための仕様
